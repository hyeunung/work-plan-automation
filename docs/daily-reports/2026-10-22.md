  - (상세: 주요 진단 내용)
  - (상세: upstream 블록 없이 proxy_pass <http://api:8000/;로|바로가기> Docker Compose 서비스에 직접 연결하는 구성은 유효하며, 프론트는 상대 경로 /api를 사용하므로 운영 빌드에 별도 API URL 환경변수가 필요하지 않음을 확인했다.)
  - (상세: Nginx의 내부 연결 대상 api:8000과 애플리케이션이 검증하는 외부 Host·Origin은 서로 다른 값이다. Nginx가 원래 헤더를 보존하면 백엔드는 사용자가 브라우저에 입력한 공개 접속 주소를 기준으로 요청을 검증한다.)
  - (상세: 실제 접속 주소가 <http://165.229.157.116:8001이므로|바로가기> PUBLIC_BASE_URL도 같은 주소로 맞추고, 일반 IP의 HTTP 접속에서는 COOKIE_SECURE=false가 필요하다. 요청을 보내는 클라이언트 측 공인 IP는 PUBLIC_BASE_URL에 사용하지 않는다.)
  - (상세: 현재 비로컬 HTTP 주소를 거부하는 설정 검증 로직이 있어 환경변수만 변경하면 애플리케이션 시작이 실패할 수 있다. 명시적인 비보안 HTTP 허용 옵션을 추가하거나, 앞단에서 HTTPS를 종료하는 운영 구성을 마련해야 한다.)
  - (상세: HTTP로 Nginx에 직접 연결하는 동안에는 X-Forwarded-Proto를 https로 고정하지 않고 실제 요청 스킴을 전달하도록 구성해야 한다. Compose가 기대하는 Nginx 설정 파일 경로와 실제 인계 파일 경로도 일치 여부를 확인해야 한다.)
  - (상세: 현재 상태)
  - (상세: 코드와 배포 설정을 기준으로 API 접근 실패 원인을 PUBLIC_BASE_URL·Host/Origin 검증·Secure 쿠키·전달 프로토콜 불일치로 좁혔다. 세션에서는 파일을 수정하거나 컨테이너를 재배포하지 않았으므로 실제 서버 반영 상태는 확인되지 않았다.)
  - (상세: 후속 확인 항목)
  - (상세: WAS 환경변수와 백엔드의 비로컬 HTTP 허용 정책을 반영한 뒤 이미지를 다시 빌드하고 관련 컨테이너를 재생성한다.)
  - (상세: 실제 마운트된 Nginx 설정에 전달 헤더를 반영하고 재시작한 뒤 /api/auth/me가 Host 차단 400 또는 프록시 실패 502가 아닌 인증 필요 401을 반환하는지 확인한다.)
